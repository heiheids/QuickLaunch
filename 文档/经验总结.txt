QuickLaunch 开发经验与踩坑总结（截至 v1.0.4）
================================================================

一、本次修复的核心教训
----------------------------------------------------------------
【坑 1】把“快捷方式”当文件本身存起来，是最自然的错误做法。
        拖放拿到的只是 .lnk 路径，看起来能启动，但源头一删就断。
        正确心智模型：快捷方式是“线索”，入库前必须解析成真实目标。
        同类问题还有：.url、.website、Steam 的 .url 快捷方式。

【坑 2】IShellLinkW 虚表槽位极易错位。
        IUnknown 三个槽位之后依次是：
        3 GetPath / 4 GetIDList / 5 SetIDList / 6 GetDescription /
        7 SetDescription / 8 GetWorkingDirectory / 9 SetWorkingDirectory /
        10 GetArguments / 11 SetArguments / 12 GetHotkey / 13 SetHotkey /
        14 GetShowCmd / 15 SetShowCmd / 16 GetIconLocation /
        17 SetIconLocation / 18 SetRelativePath / 19 Resolve / 20 SetPath
        只要少定义/多定义一个未用槽位，调用就会跳到别的函数上，
        表现通常是“崩溃”或“返回垃圾字符串”，而且没有编译期报错。
        做法：未使用的槽位统一用 *const c_void 占位，保持下标不变。

【坑 3】GetPath 的 fFlags 用 0（默认）时才会展开 %SystemRoot% 一类环境变量；
        传 SLGP_RAWPATH 会拿到未展开的原始字符串，直接拿去启动会失败。

【坑 4】UWP / 应用商店应用的快捷方式 GetPath 返回空串。
        此时不应报错，更不应把条目删掉，要原样保留 .lnk。

【坑 5】链式快捷方式（.lnk 指向 .lnk）真实存在，
        解析必须限量递归（这里 4 层），否则遇到环会死循环。

【坑 6】历史数据迁移要“只修能证明的”：
        只处理 .lnk 文件仍然存在的条目；文件都不在了就千万别猜，
        宁可保留原样让用户自己处理。

二、Windows / 构建环境踩坑
----------------------------------------------------------------
【坑 7】Rust GNU 工具链不带 windres，因此 res\app.rc 编不了，
        exe 会丢掉图标。三条路：
        a. 装 MinGW/MSYS2 提供 windres（要外网、体积大）；
        b. 纯 Rust 手写 .rsrc 段目标文件（本工程采用，零依赖）；
        c. 干脆不带图标（不可接受）。
        注意：GNU ld **不接受** .res 文件（"file format not recognized"），
        必须是 COFF 目标文件（.o），这是关键区别。

【坑 8】PE32+ 的可选头里 NumberOfRvaAndSizes 在偏移 108，
        数据目录从 112 开始；PE32（32 位）才是 92 / 96。
        用错偏移会读到 0，误判“资源表没写进去”。

【坑 9】没有 VS 生成工具时，选 x86_64-pc-windows-gnu 目标即可，
        rustup 的 rust-mingw 组件自带链接器，不需要安装 VS Build Tools。

【坑 10】rustup-init.exe 下载不完整时表现为
         “%1 不是有效的 Win32 应用程序”，而不是明确的解压错误。
         校验方法：读文件头两个字节是不是 "MZ"，以及大小是否与官方一致。
         另外这台机器上 Invoke-WebRequest 会卡住不动，curl.exe 反而正常。

三、工程习惯
----------------------------------------------------------------
【习惯 1】改动前把源码打成 zip 放进 备份\，并在 QuickLaunch工程备份.txt
          写清“即将做什么”，出问题能精确回退。
【习惯 2】新功能先写能被机器验证的测试（本版用 COM 现场造 .lnk 再解析），
          比“打开界面用鼠标拖一下”可靠得多，也便于回归。
【习惯 3】所有新增入口收敛到同一个函数（add_path），
          避免“拖放能用、对话框不行”这类不一致。
【习惯 4】模块边界按“职责”切，不按“行数”切：shortcut.rs 只负责解析，
          不碰界面、不碰数据库写盘（迁移函数除外，且只改字段）。
【习惯 5】大文件不整读：定位问题时先 grep 命中行号，再 read 局部区间。

四、下一步
----------------------------------------------------------------
1. 多语言：把硬编码中文抽到 lang\ 配置文件，中英各一份，按系统语言自动选择。
2. app.rs 继续拆分（布局 / 菜单 / 设置 / 启动）。
3. 快捷方式解析加缓存，避免一次拖入几十个时重复走 COM。

五、v1.0.5 新增踩坑
----------------------------------------------------------------
【坑 11】ShellExecuteW(hwnd, "properties", ...) 对 exe 和文件夹返回 31，
        不会弹错误框，表现就是“点了没反应”；只有 .lnk 能用。
        正确做法：ShellExecuteExW + SEE_MASK_INVOKEIDLIST(0x0C)。
        验证方法：实测返回值，>32 才算成功，<=32 都是错误码。

【坑 12】“属性”到底该开谁，是个产品语义问题。
        把快捷方式解析成目标程序之后，如果属性直接开目标 exe，
        用户会觉得“我要的是快捷方式的属性”。
        结论：数据结构要留一手——额外存 src（原始快捷方式路径），
        属性优先开 src，src 不存在再回退目标。
        教训：做“解析/归一化”时，原始输入不要丢，往往是别的功能要用的。

【坑 13】给 links.txt 加列要向后兼容：新列加在末尾，读取用 f.get(i)
        带默认值；旧 13 列数据加载后新字段为空即可，不需要迁移脚本。

六、v1.0.6 图标踩坑（手写 PE 资源的两个致命细节）
----------------------------------------------------------------
【坑 14】资源目录项指向子目录时，偏移最高位（0x80000000）必须置 1。
        漏了它，根目录条目会被当成“数据项”，整棵资源树直接解析失败。
        典型症状：资源表 RVA、段大小全都正常，图标却是错的/通用图标。
        排查方法：打印资源段前 48 字节，看目录项偏移是否带 0x80000000。

【坑 15】IMAGE_RESOURCE_DATA_ENTRY.OffsetToData 存的是 RVA（相对镜像基址），
        而目录项的偏移是段内相对偏移。手写 COFF 时必须给这些字段加
        IMAGE_REL_AMD64_ADDR32NB(0x0003) 重定位 + 一个 .rsrc 段符号（带 aux 段定义），
        链接器才会补上段 RVA。不加重定位 = 把段内偏移当 RVA 用，数据全指向错处。

【坑 16】验证图标别只看“exe 变大了 / 资源表 RVA 非 0”，这两种情况在
        资源树写坏时照样成立。要直接解析资源树、把图像数据与源 .ico 逐字节比对。
        更别只靠 ExtractAssociatedIcon 看尺寸——壳层有缓存，也看不出错位。

【坑 17】PowerShell 里遍历大字节数组做输出，很容易把整块数组打进控制台，
        导致输出爆炸/任务中断。这类校验改用 Rust 写示例程序，类型明确、输出可控。

【经验】“恢复之前图标”这种诉求，最省事的定位方式是拿旧产物当基准做逐像素对比。
        本例：旧 1.0.3 exe（仍在运行，可直接取 Path）与新 exe 比，
        差异 910/1024 -> 修复后 0/1024，结论一目了然。

七、v1.0.7 网址图标踩坑
----------------------------------------------------------------
【坑 18】favicon 不能只赌 /favicon.ico。
        实测：bilibili/baidu/zhihu/qq 有根 favicon.ico；
        rust-lang.org、example.com 返回 404，图标写在首页 HTML 的
        <link rel="icon" href="..."> 里。必须做 HTML 备用发现。

【坑 19】很多站点的 favicon.ico 内容其实是 PNG（rust-lang、baidu 都是）。
        如果按 URL 后缀一律存成 .ico，icons.rs 会走 PrivateExtractIconsW，
        而它只认真正的 ICO 资源 —— 结果是“抓到了但显示不出来”
        （实测 5 个里 2 个提取失败）。
        正确做法：按字节头判断真实格式再决定扩展名。
        ICO=00 00 01 00 / PNG=89 50 4E 47 / JPEG=FF D8 FF / GIF=GIF8 / BMP=BM。

【坑 20】网络请求绝不能放在 UI 线程。WinHTTP 单次超时就 3 秒，
        连着试几个候选会卡住整个消息循环，用户会以为程序死了。
        做法：worker 线程 + mpsc 队列 + PostMessageW 唤醒，
        线程里绝不碰 HWND/界面对象。

【坑 21】别为测试复刻一套抓取逻辑。
        最初 examples 里自己写了个“简化版 fetch”，结果它失败但产品代码成功，
        白白排查半小时。测试必须调用产品里同一个函数。

【坑 22】PowerShell 的 .Replace() 对含中文/换行的长字符串很容易因
        CRLF 差异静默失败（返回原串）。改代码优先用编辑工具，
        用脚本替换后必须回读确认，不能只看“没有报错”。

【坑 23】用 URL 的 www. 前缀做显示名会显得啰嗦，但也不能直接改写 URL ——
        有些站点（尤其老的）必须带 www 才能访问。只改显示名最安全。

八、v1.0.8 分割线可调
----------------------------------------------------------------
【经验 1】布局常量别藏硬下限。
        分组栏原来写死 max(font_size*4+36)，本意是"别太窄导致字画不下"，
        但用户需求是"最窄只显示一个字"，硬下限直接把路堵死了。
        改成按字号算：min = font_size + 10（最少 18）。
        凡是"想要更自由"的诉求，先找有没有这种拍脑袋的硬编码夹取。

【经验 2】拖动类交互要放进已有的三件套里，别另造一套：
        WM_LBUTTONDOWN 记录状态 + SetCapture
        WM_MOUSEMOVE   处理并 repaint
        WM_LBUTTONUP   清状态 + save_conf
        照抄窗口边缘缩放（resize_dir）的写法最稳，也最少引入新 bug。

【经验 3】命中测试要"抢在前面"。
        分割线横跨分组栏右边界，而分组项矩形和内容区也会覆盖附近区域，
        所以 Split 的判定必须写在 gitems/body 之前，否则永远命中不到。

【经验 4】拖动时别忘置脏缓存键。
        这个程序把布局和静态底图都做了缓存（lkey / bgkey），
        只改 conf.group_w 不置脏，画面不会更新——会以为"拖不动"。

【经验 5】GUI 功能没法用鼠标自动点，但**能**写单测。
        App::new(null, tmp) 不建窗口也能跑布局与命中测试，
        于是"分割线能否点中""夹取到最窄是多少"都能被机器验证，
        比"人工拖一下看看"可靠得多。

九、v1.0.9 窗口阴影调窄调淡
----------------------------------------------------------------
【坑 24】阴影"变窄"不等于"变淡"。
        8 层阴影叠出来的浓度取决于层间距：带宽从 12 减到 6 时若只改带宽、
        层间距按比例压缩，各层会挤在一起，边缘反而更黑（实测 179 -> 214）。
        正确做法：带宽、层间距、起始 alpha 三者一起调。
        最终 12px/alpha18 -> 6px/alpha6，边缘 179 -> 232，才是"又窄又淡"。

【坑 25】阴影偏移量必须跟带宽一起缩放，否则最外层画到画布外，
        被裁成一条硬边——看起来像"黑框"而不是阴影。

【坑 26】想把界面画出来核对，得先自己初始化 GDI+。
        测试进程不走 main()，没调 GdiplusStartup 时所有 Gdip* 调用都静默失败，
        导出的位图全白，很容易误判成"代码没生效"。
        另外 GDI+ 会缓冲绘制，读像素前要 GdipFlush(g, 1)。

【经验 6】界面效果别靠肉眼猜：把静态层导出成 BMP/PNG，
        再读取某一行的亮度剖面做数字对比（改前 179 / 改后 232），
        比"看着差不多"可靠得多，也能写进提交说明里。
